# mailverify 设计文档

## 设计目标

- 批量邮箱认证不依赖浏览器页面生命周期。
- 应用重启后自动恢复未完成任务。
- 将 Microsoft token 端点并发限制在可控范围内。
- 重新认证与正在执行的任务之间不产生同一邮箱并发竞争。

非目标：提供分布式多实例调度、保存 OAuth 错误详情、替代 `mailfetch` 的协议实现。

## 方案选择

采用“数据库状态作为队列 + 进程内固定 worker 池”。`unverified` 是待处理状态，worker 领取时原子更新为 `verifying`，完成后写入 `verified` 或 `verify_failed`。

曾考虑纯内存 channel，但它无法在进程重启后恢复；也考虑新增任务表，但当前任务与邮箱一一对应，复用已有状态字段更简单，且不需要迁移额外数据结构。

## 核心流程

```text
导入/重新认证
    │
    ▼
unverified ──worker 领取──> verifying ──成功──> verified
                                  └────失败──> verify_failed

应用启动：verifying ──恢复──> unverified
```

## 关键决策

| 决策 | 理由 | 影响 |
|---|---|---|
| 默认 10 worker | 保持原页面批量验证的并发上限 | 并发集中在服务端，可统一控制 |
| 每次领取使用条件更新 | 避免两个 worker 领取同一记录 | SQLite 下无需长事务持锁 |
| 进程内记录 active ID | 重新认证进行中的邮箱时避免重复并发 | 单实例部署有效 |
| 完成更新要求状态仍为 `verifying` | 不覆盖重新认证产生的新 `unverified` 状态 | 旧请求结果会被安全丢弃并重新执行 |
| 空闲 worker 定时扫描并接受 wake 信号 | 防止遗漏唤醒，同时降低空轮询 | 最迟约 5 秒发现外部插入任务 |

## 已知限制

- 当前按单应用实例设计；多个服务实例共享同一 SQLite 时，进程内 active 集合不能跨实例协调。
- 邮箱状态保存最终成功/失败，`verify_error` 保存不含凭据的最近一次失败原因，便于前端区分缺少凭据、OAuth 失效和临时服务错误。
- 服务停止会取消当前 HTTP 请求；下次启动会恢复遗留任务。

## 安全考量

- worker 日志不输出邮箱密码、refresh token 或 access token。
- OAuth 凭据只从现有数据库模型传给 `mailfetch`，不复制到任务表。
- 所有触发接口继续受现有 Bearer token 中间件保护。
